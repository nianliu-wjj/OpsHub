# RBAC 数据删除策略

决策日期：2026-11-18。本决策区分身份和配置主数据、当前授权关系、不可变日志以及派生缓存。逻辑删除字段统一使用 `is_deleted`（0未删除、1已删除），不因为某张表属于同一模块就机械地采用同一种删除方式。

## 删除策略决策表

| 数据 | 采用方式 | 版本字段 | 本次实现 |
| --- | --- | --- | --- |
| sys_account 账号 | 逻辑删除 | version，用于修改和删除的乐观锁 | 标记删除并清理角色绑定，登录查询排除 |
| sys_role 角色 | 逻辑删除 | version，也用于整组授权的并发控制 | 标记删除并清理账号绑定和菜单绑定 |
| sys_menu 菜单/操作权限 | 逻辑删除 | version | 有有效子节点时拒绝删除，标记删除并清理角色绑定 |
| sys_account_role 账号角色绑定 | 物理删除 | 无；并发控制由账号主行 version 承担 | 整组替换，去重后插入 |
| sys_role_menu 角色权限绑定 | 物理删除 | 无；并发控制由角色主行 version 承担 | 整组替换，去重后插入 |
| sys_login_log 登录日志 | 保存期内不可变，到期物理清理 | 无；不允许编辑 | 本次仅提供查询，不提供单条删除或清理接口 |

## 为什么账号使用逻辑删除

账号 ID 是身份的稳定标识。即使账号退出组织或停止使用，历史操作、审批记录和业务责任仍需要能够对应到同一身份，物理删除会使后续查询只能看到无上下文的 ID。保留账号主行能为历史查询提供关联依据，并避免重新注册后被误认为原账号。

逻辑删除必须立即阻止认证与授权：凭据查询过滤 is_deleted=0，方法权限每次重新检查账号状态；删除事务同步清理当前角色绑定并递增缓存版本。只在管理列表中隐藏账号而继续允许认证不符合本方案。

账号的“禁用”和“删除”不同：暂时停用应改 enable，不清除授权；删除表示退出当前账号管理，不再保留有效绑定。保留 deleted 账号也不意味着永久保留全部个人信息。后续需根据组织的数据保留要求对邮箱、姓名等字段做脱敏或匿名化；物理清除需审核历史引用、归档和备份策略，不能由普通账号删除接口承担。

## 为什么角色与菜单使用逻辑删除

角色和权限码是管理配置，误删可能影响大量账号。保留主记录便于定位历史配置、解释审计事件和开展经过审批的恢复。相比几条角色/菜单主行所占空间，调查身份和权限变更的成本更高，保留主数据的收益更明确。

但是逻辑删除不等于完整版本历史。当前主表保留的是最后状态，字段修改前的完整历史由审计承担；此次删除接口没有自动恢复接口。恢复主记录时不能自动恢复旧绑定，否则可能重新授予已撤销的权限，必须重新审核并显式授予。

菜单父子关系需要维护：只要还有有效子菜单就拒绝删除父菜单，避免导航树成为孤儿；逻辑删除节点不再参与授权计算。菜单隐藏只影响展示，不能当作删除或撤权。

用户名、角色 code、权限 code 的唯一键仍覆盖逻辑删除记录，保留值暂不可复用。这能避免新的同名账号/权限码与历史身份混淆；若后续确需复用，应设计单独的归档标识或有条件唯一性方案，并明确审计身份区分方式，不能仅将 is_deleted 加进联合唯一键——多次删除同一编码会再次撞上唯一键。

## 为什么两张关联表使用物理删除

绑定行只描述“现在授予了哪项权限”，没有独立业务身份，稳定主键的历史价值远低于账号和角色。绑定的撤销历史应作为授权变更事件记录，而不是让每一条当前授权查询都扫描累积的失效绑定。

采用逻辑删除会要求所有联表永远加上关联行 is_deleted=0，否则一处漏条件就可能重新授予已撤销权限。它还使唯一键(account_id,role_id)/(role_id,menu_id)与重新授权相冲突，需要额外的恢复/upsert语义。对于高频解绑重绑，物理删除可以保持关系表大小与当前授权数量成比例，并直接表达撤销结果。

因此整组替换使用删除原关系+插入去重后的新关系，全部在事务内完成。账号、角色或菜单逻辑删除时也物理删除涉及的关系。关联表本身不设置 version：HTTP 请求对账号或角色主行提交 expected version，推进主行版本，避免两个授权编辑请求无声覆盖。记录关系变更的审计事件必须独立于关联表保存；当前 OpsLog 记录操作对象和结果，若未来要求完整还原每一次授权集合，应扩展审计载体保存变更前后集合，不能声称仅凭当前表就能还原历史授权。

## 为什么日志不做逻辑删除

登录和审计日志是不可变事件，version 没有乐观锁价值，因为业务不应修改一条历史事件；is_deleted 会让清理仅隐藏记录，实际容量和敏感数据驻留时间仍持续增加。它还会使“记录是否存在”与“查询是否显示”不一致，削弱调查过程的可解释性。

保存期内不向普通 API 提供修改和删除。保存期到期后，应按组织合规要求先归档再分批物理清理，或在采用时间分区的未来版本中删除已归档的旧分区。保留期由部署方结合安全调查、合同和存储成本决定，不在代码中假定一个适用于所有组织的天数。本次只开发登录日志查询，不实现未经确定保留规则的定时删除任务。

文件审计沿用已有容量和时间滚动配置，运维部署应核对它是否满足实际审计保留要求；日志备份中的副本也需要遵循相同生命周期。账号逻辑删除不级联删除其历史登录或操作审计。

## 应用层关联校验与并发一致性

数据库不定义 FOREIGN KEY。服务在写事务中锁定统一 RBAC 版本行，然后检查账号/角色/菜单是否存在且未删除、菜单祖先是否成环，再修改绑定或删除。这样可在多个应用实例之间串行化当前低频的权限图修改，防止“检查目标存在后，另一事务先删除目标”的竞争。

所有修改接口和删除接口使用主行 version 条件更新，过期请求返回 A0409。事务提交前递增全局缓存版本，新请求不会使用旧权限快照。事务回滚时主表、绑定和全局版本一同回滚。直接 SQL 导入或其他服务如果绕过同一锁和校验协议，数据库不会自动保护关联完整性；需在运维规范中禁止绕过服务随意改权限。

主表逻辑删除必须显式过滤，生成实体配置 MyBatis-Flex isLogicDelete=true，自定义 SQL 也独立写明 is_deleted=0。两者不能互相替代。未来重新生成实体时只识别实际拥有 is_deleted/version 的主表，不给关联表和日志额外注入这些列，以免 SQL 查询出现不存在字段。

## 不采用的统一策略

全部物理删除会损失主身份及配置上下文；全部逻辑删除会使关系表积累失效授权、增加漏过滤风险，并无法释放日志容量。按数据含义分别处理，能让权限撤销、历史解释和容量管理各自保持清晰的行为边界。
