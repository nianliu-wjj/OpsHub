## 一、项目定位与背景

### 1.1 项目使命

OpsHub 是一款面向 **MySQL、Redis 等基础运维组件**的 Web 端统一运维管理平台：

- **收敛操作入口**：把原本分散在命令行（mysql/redis-cli）、客户端工具（Navicat、DBeaver、RedisInsight）中的数据库与缓存运维操作，汇聚到一个直观的可视化界面；
- **管控高危变更**：DDL 变更、实例参数调整、数据清理等高危操作经平台统一受理、审批、审计留痕，杜绝"裸连生产库随手改"；
- **统一凭据治理**：数据库账号口令不再散落在个人笔记本的连接配置里，凭据集中在平台侧保管与下发。

### 1.2 交付节奏

| 阶段 | 范围 | 状态 |
| --- | --- | --- |
| 阶段 ① | 技术选型与工程骨架（依赖治理、多模块分层、日志与配置基座） | **本文档（§3 + 已落地工程）** |
| 阶段 ② | 总体架构与领域模型（实例/凭据/操作工单/审计的领域建模） | 规划中 |

## 二、复杂度识别（三板斧第一步：有的放矢）

架构设计的本质目的是**解决软件系统的复杂性**，选型之前必须先回答"本项目的复杂度主要是什么"——识别错了复杂度，后面所有选型都是在错误的方向上精益求精。

### 2.1 复杂度候选评估

架构复杂度通常来源于高性能、高可用、可扩展、安全等几个方面，按下表逐项排查（《架构篇》经验法则：**一次只解决最主要的一个**）：

| 复杂度候选 | OpsHub 的实际情况 | 是否主复杂度 |
| --- | --- | --- |
| **高性能** | 管理后台形态：操作由运维人员发起，QPS 量级个位数到百级；远低于交易系统 | ❌ 不是 |
| **高可用** | 平台属**管理面**：OpsHub 停机**不影响**被管 MySQL/Redis 实例自身运行（业务面与管理面天然隔离）——最坏情况是"运维操作暂时无法发起"，而非业务资损 | ❌ 弱诉求（参考 §4） |
| **可扩展（组件维度）** | 今天接 MySQL、Redis，明天可能接 Kafka、ES、ClickHouse——**每类组件都带着不同的连接协议、操作语义、风险等级**，接入方式必须可插拔 | ✅ **第一主复杂度** |
| **可扩展（实例维度）** | 一个组件类型下要管理成百上千个实例：**多目标实例动态建连 / 连接池治理 / 实例级隔离**是数据访问层的硬需求 | ✅ 第二主复杂度（与第一项同根） |
| **安全性 / 资损防护** | 平台直接触达生产实例：高危 DDL 误操作、凭据泄漏、SQL 注入面扩大——一次误操作可能直接打挂业务库 | ⚠️ 强约束（作为**设计红线**贯穿，不作为技术选型的排序复杂度） |

### 2.2 结论

1. **主要复杂度 = 可扩展性**，且呈两个维度：组件类型可插拔（接入 Kafka/ES 不改主干）、目标实例可规模化（动态多数据源是数据访问层的第一选型依据）；
2. **安全性是硬约束**而非排序复杂度：不追求"多安全的组件"，而是每一层选型都要内建安全能力（凭据注入、参数校验、审计留痕）；
3. **反面教训规避**（《架构篇》过度设计案例）：不对标工业级一体化管控平台的体量设计 40 个子系统——OpsHub 当前量级下，**单模块群 + 可插拔接入点**即可满足三年内演进。

> 该结论直接压缩选型空间：**多数据源动态连接能力成为 ORM 选型的一票指标**（见 §3.2）；Web 框架无需为虚拟化容器/云原生启动速度付出额外复杂度（见 §3.1）。

## 三、技术选型（360 度环评）

### 3.0 选型原则与评估框架

所有备选方案用同一组质量属性环评（《架构篇》360 度环评），并遵守三条设计原则：

| 原则 | 本项目的具体化 |
| --- | --- |
| **合适优于先进** | 管理后台的量级不选"为每秒十万请求而生"的技术；选型服务于"组件接入效率 + 操作安全性" |
| **简单优于复杂** | 能用官方缺省（Lettuce、Logback）就不引入新决策点；每个三方件必须回答"能力唯一归属到哪个模块" |
| **演进优于一步到位** | 选当下合适的，同时保证**接口稳定 + 实现可替**：仓储接口在领域层、实现在数据访问层，ORM 可整体替换而不上溯 |

**评估维度**：性能可用性 / 团队投入与上手成本 / 安全性（漏洞面与响应速度）/ 可扩展性（组件接入维度）/ 演进风险（版本升级与生态适配）。

---

### 3.1 运行时基座：Spring Boot 3.5.x（*选定*）

**备选方案**（差异点为架构级，非参数级）：

| 方案 | 架构差异点 |
| --- | --- |
| A. Spring Boot 3.5.x（Spring Framework 6.2 / Jakarta EE 10） | 云原生一代主流；生态适配最深 |
| B. Spring Boot 4.x（Spring Framework 7 / Jakarta EE 11） | 下一代主线（2025-11 GA）；生态中间件适配仍在追赶 |
| C. Solon v3 | 国产轻量容器：启动快、内存省（约为 Spring Boot 的 1/2~1/3） |
| D. Quarkus 3.x + GraalVM | 云原生极致启动（数十 ms）与低内存，代价是反射生态的额外配置面 |

**360 度环评**：

| 维度 | A`SB 3.5` | B`SB 4` | C`Solon` | D`Quarkus` |
| --- | --- | --- | --- | --- |
| 生态适配（ORM/连接池/监控） | ★★★★★ 全量官方 starter | ★★★ 主流件陆续适配中 | ★★ 需自作集成 | ★★ 反射生态配置成本高 |
| 团队上手 | ★★★★★ 业界事实标准 | ★★★★ API 差异小但文档处于过渡期 | ★★ 心智新栈 | ★★ GraalVM 知识负载 |
| 启动/内存 | 满足（实测 1.2s 启动，见 §4） | 同左 | 优 | 极优 |
| 运维平台特有诉求 | 多数据源/连接治理生态成熟 | 同左 | 多数据源生态薄 | Native Image 对"动态建连任意实例"敌意大 |
| 演进风险 | 3.5 维护线内平滑；→4.x 路径已有官方迁移指南 | 本身即未来 | 国产生态单点 | 红帽主导，路线稳但范式跳跃 |
| **已知漏洞状态** | **3.5.16 汇集全部已公开 CVE 修复** | GA 时间短、历史包袱少 | — | — |

**取舍说明**：

- **选 A 的理由**：OpsHub 的复杂度在"多组件/多实例接入"而非启动速度（管理面无需秒级弹性伸缩）；MyBatis-Flex 官方提供 `mybatis-flex-spring-boot3-starter`，连接池、校验、监控全部官方级适配——**合适原则**直接收敛到 A；
- **放弃 B**：4.x GA 时间尚短，中间件生态（尤其 ORM 与连接治理类）适配声仍在追赶期，运维平台自己不能当生态白鼠——但 JDK/Jakarta API 用法与 4.x 无裂痕，**演进通道保留**（升级是依赖版本号变更，非重写）；
- **放弃 C/D**：两者全力打的是"启动/内存"指标——那不是本系统的主复杂度（§2.2 已经论证）。为不存在的诉求承担新栈心智成本，违反**简单原则**。

**落点版本**：`3.5.16`（3.5 维护线最新 patch，Spring Framework 6.2.19）。

### 3.2 ORM/数据访问：MyBatis-Flex（*选定*）

这是本次选型中**与业务复杂度耦合最深**的一项。OpsHub 的数据访问有两类完全不同的形态：

1. **平台自身元库**：实例注册表、凭据托管、操作审计——常规 CRUD，单库；
2. **目标实例在线访问**：对**成百上千个动态注册/下线的 MySQL 实例**建立连接，执行在线查询、慢日志分析、状态巡检（`SHOW PROCESSLIST`、`information_schema`、`PERFORMANCE_SCHEMA` 等运维语句）——SQL 形态偏原生，连接对象动态多变。

形态 2 决定了一票指标：**多数据源必须原生、动态、可编程**。

**备选方案**：

| 方案 | 多数据源能力 | 运维语句适配度 | 编译期安全 |
| --- | --- | --- | --- |
| A. MyBatis-Flex | ✅ **内置 `FlexDataSource` 多数据源 + `DataSourceKey` 编程切换，无需任何额外组件** | ✅ 保留原生 MyBatis 语法直出（`SHOW ...`/`SELECT FROM information_schema`） | ✅ APT 生成表元数据（`TableDef`），Query 链式构造是**编译期强类型** |
| B. MyBatis-Plus + dynamic-datasource | ⚠️ 需引入第三方 `dynamic-datasource-spring-boot-starter` 叠加实现 | ✅ 同为 MyBatis 语法 | ⚠️ `QueryWrapper` 为运行时字符串拼接，字段名改动无编译期报错 |
| C. Spring Data JPA（Hibernate 6） | ⚠️ 多 `EntityManagerFactory` 装配繁琐，动态注册实例不友好 | ❌ 面向对象映射模型天然不擅长 `SHOW`/系统表类语句 | ⚠️ JPQL 编译期校验有限 |
| D. JOOQ | ✅ 可编程构造 | ✅ 强类型 DSL | ✅ 最强 |
| | 但：开源版 License 仅覆盖开源数据库，未来若接入商业库需商业授权；社区中文资料少 | | |

**360 度环评**：

| 维度 | A`MyBatis-Flex` | B`MyBatis-Plus` | C`JPA` | D`JOOQ` |
| --- | --- | --- | --- | --- |
| 动态多数据源（一票指标） | ★★★★★ 原生内置 | ★★★ 需第三方叠加 | ★★ | ★★★ |
| 运维语句（SHOW/系统表） | ★★★★★ 原生 SQL 直出 | ★★★★★ | ★★ | ★★★★ |
| 编译期字段安全 | ★★★★★ APT TableDef | ★★ Wrapper 运行时 | ★★★ | ★★★★★ |
| 生态规模 | ★★★ 上升期（1.11.x） | ★★★★★ 老牌社区 | ★★★★ | ★★ 中文区很薄 |
| License | Apache 2.0 | Apache 2.0 | Apache 2.0 / EPL | ⚠️ 开源版限开源库 |

**取舍说明**：

- **选 A 的理由**：在"动态多数据源原生支持 + 原生 SQL 适配运维语句 + 编译期安全"三项上同时达标，且不引任何第三方叠加组件——**正是第一主复杂度（可扩展/多实例）的正解**；牺牲的是 MyBatis-Plus 的更大社区与插件面，换来的多数据源能力恰是本平台命脉；
- **放弃 D（JOOQ 编译期安全其实最强）**：License 结构与未来组件演进方向冲突（Kafka/ClickHouse 后的商业库诉求）、中文社区见效成本高，**合适原则**否决；
- **放弃 C**：领域模型稳定、以实体生命周期为中心的系统才吃 JPA 红利，元库之外的场景是它的短板。

**落点版本**：`mybatis-flex-spring-boot3-starter 1.11.8`。

### 3.3 JSON 序列化：fastjson2（*选定*）

**该选型多了一层工程纪律问题**：Spring Boot web starter 默认携带 Jackson，业务若再用 fastjson2 即"同能力双实现"（编码规范 §2.5 明令禁止：行为不一致、漏洞面扩大）。因此本节不仅选型，还要处理**两库并存冲突的收敛**。

**备选方案**：

| 方案 | 说明 |
| --- | --- |
| A. fastjson2 统一（HTTP + 业务同库） | 需替换 Spring 默认转换器：`fastjson2-extension-spring6` + exclusion Jackson |
| B. Jackson 统一（放弃 fastjson2） | 缺省不动，业务侧也用 Jackson |
| C. 双库并存（各管一摊） | ❌ 违反编码规范，仅列出作对照 |

**环评**：

| 维度 | A`fastjson2 统一` | B`Jackson 统一` |
| --- | --- | --- |
| 序列性能 | ★★★★★（多轮公开基准长期第一梯队） | ★★★★ |
| API 心智 | ★★★★★ `JSON.toJSONString/to` 一个入口，`JSONObject` 天然有序 | ★★★ 注解体系（`@JsonInclude`...）碎片化，属性迁移成本 |
| 团队既有资产 | ✅ 历史代码与工具沉淀在 fastjson2 侧 | 需二次翻新 |
| Spring 生态贴合力 | ★★★ 经 extension 适配 | ★★★★★ 原生缺省 |
| 漏洞体质 | fastjson2 为**全量重写架构**（非 fastjson1 改良版）：不存在 autoType 历史漏洞系；autoType 默认关闭 + 白名单机制 | 使用面最大、CVE 披露频度最高（响应也快） |
| 中文文档生态 | ★★★★★ | ★★★ |

**取舍说明**：选 **A**。理由：① 团队资产与心智在 fastjson2 侧（**合适原则**）；② 性能冗余充足；③ 漏洞体质干净（**安全性红线**——fastjson2 2.0.x 线为重写架构，与 1.x 的反序列化漏洞史没有代码血缘）。代价是多做了一个"替换默认转换器"的动作——本工程已经把代价付清：

- POM 层：`spring-boot-starter-web` 声明 exclusion 剥离 `spring-boot-starter-json`；
- 装配层：启动装配层注册 `FastJsonHttpMessageConverter`，并预设全工程统一序列化策略——**Long → String**（实例 ID 超过 JS `Number.MAX_SAFE_INTEGER`（2^53）会静默丢精度，运维对象 ID 的唯一性不允许）、null 值保键输出、统一日期格式 `yyyy-MM-dd HH:mm:ss`。

**落点版本**：`fastjson2 2.0.66` + `fastjson2-extension-spring6 2.0.66`。

### 3.4 Redis 客户端：Lettuce（*选定*）

平台对 Redis 有两类动作：管理自身缓存（会话、实例状态镜像），以及对**多个远端目标 Redis 实例**执行诊断命令（`INFO`、`SLOWLOG`、`--scan`）。

| 方案 | 差异点 |
| --- | --- |
| A. Lettuce（Spring Boot 官方缺省） | Netty 多路复用、单连接线程安全、同步/异步双 API、零连接池依赖 |
| B. Jedis | 直连阻塞模型，命令并发依赖 commons-pool2 连接池 |
| C. Redisson | 自带分布式数据结构（锁/布隆/延迟队列）全家桶 |

**取舍说明**：

- 选 **A**：官方缺省 = **简单原则**零决策冗余；运维平台的 Redis 诊断命令是短平快交互，Lettuce 单连接多路复用模型最省资源；多实例诊断场景下，Lettuce 的 `RedisClient` 可编程直连任意目标实例，与多数据源治理同构；
- 放弃 C：分布式锁/延迟队列当前无场景（操作工单用数据库状态机即可承载），不做"为未来可能性"的依赖引入；
- 放弃 B：阻塞模型在"平台侧聚合多个实例状态巡检"场景要多付一整套连接治理成本。

**落点实现**：`spring-boot-starter-data-redis 3.5.16`（内含 Lettuce 6.6.0，版本由 Spring Boot BOM 统一裁决）。

### 3.5 对象转换：MapStruct（*选定*）

运维平台的转换场景密集：`Request ↔ Model ↔ DTO`（契约边界）、`DO ↔ Model`（数据访问边界，编码规范：对外只暴露仓储接口，DO 不出数据访问层）。

| 方案 | 差异点 |
| --- | --- |
| A. MapStruct | **编译期**生成 getter/setter 直调代码，零反射 |
| B. Spring/Apache BeanUtils | 运行时反射拷贝，字段静默漂移 |
| C. 手写转换器 | 性能同 A，但字段增删需人工同步维护 |

**取舍说明**：选 **A**。运维对象字段多变（实例属性随版本扩展），转换器必须**跟着字段编译期走**——字段改名/删除时 MapStruct 直接编译失败，反射方案则是运行期静默丢字段（对审计/巡检数据完整性是事故级隐患）。与 Lombok 协同需引入 `lombok-mapstruct-binding`（本工程编译器配置已统一处理处理器顺序）。性能与手写持平（生成代码 v.s. 螺栓拧紧的 getter 链）。

**落点版本**：`mapstruct 1.6.3`（1.7 尚处 Beta，不进生产）。

### 3.6 通用工具库：commons-lang3（*选定*）

| 方案 | 差异点 |
| --- | --- |
| A. commons-lang3 | Apache 基金会维护、**零传递依赖**、只提供核心工具（StringUtils/Tuple/时间） |
| B. Hutool | 国产全家桶（HTTP 客户端/加密/JSON/POI...一个包打尽） |
| C. Guava | Google 系，功能强（缓存/并发原语齐全）但传递面宽 |

**取舍说明**：选 **A**。**最小依赖面原则**：OpsHub 已经做了 JSON（fastjson2）、HTTP（Spring WebClient）、ORM（MyBatis-Flex）的能力唯一归属，全家桶库与"能力唯一归属"直接冲突；commons-lang3 的 200KB 只覆盖纯函数工具，与各专有组件零重叠。工具库的第一属性是**漏洞响应**：Apache 基金会 CVE 流程工业级成熟（3.22.0 即为 CVE-2025-48924 的修复线以上版本）。

**落点版本**：`commons-lang3 3.22.0`。

### 3.7 日志实现与分通道策略：Logback + 四通道异步（*选定*）

| 方案 | 差异点 |
| --- | --- |
| A. Logback（Spring Boot 缺省） | 1.5.x 线支持 `logback-spring.xml` 环境感知（springProfile 切换装配） |
| B. Log4j2 | Log4Shell 历史阴影（已修复但审计信任回补成本）；异步 Appender 性能优 |

**取舍说明**：保留 **A（缺省）**。运维后台日志量支持业务面秒级日期切换切频度日志不大的判断（QPS 很低），Log4j2 的异步性能优势缺乏兑现场景；换实现 = 换漏洞审计认知成本，**简单原则**保留缺省。**平台对日志的真实诉求不是"更高吞吐"而是"更合理的通道纪律"**（编码规范 §18.3.1 事故复盘），已在 `logback-spring.xml` 落地：

| 通道 | Logger 约定 | 滚动/保留 | 说明 |
| --- | --- | --- | --- |
| 业务明细 | root 及业务 Logger | 天+200MB / 30d / 5GB | 排障证据 |
| 监控摘要 | 命名 Logger `MONITOR_SUMMARY` | 天+100MB / 15d / 1GB | 业务监控切面聚合摘要 |
| 数据访问 | `DAL_ACCESS` + mapper namespace | 天+200MB / **7d** / 3GB | SQL 明细量大时效短 |
| 错误明细 | 全 ERROR 复制（ThresholdFilter） | 天+100MB / **60d** / 2GB | 证据长留 |

配套四项纪律（规范 §18 的直接落地）：全通道异步 `neverBlock=true`（队列满丢弃事件、**绝不阻塞业务线程**）；`maxHistory + totalSizeCap` 双上限（防磁盘打爆）；traceId 列全链路透传（MDC）；三级分区（错误长留 / 摘要短留 / 明细中留）——**证据与摘要的成本结构不同**。

> 日志如何按通道写入、按什么方式区分路由（Logger 命名树 / 显式·隐式路由 / 级别复制）的完整机制说明，见《[日志通道设计说明](日志通道设计说明.md)》。

**日志目录策略（按环境分离锚点）**：

| 环境 | 目录 | 机制 |
| --- | --- | --- |
| dev | **工程根 `/logs`** | 构建期 Maven 资源过滤把 `@project.parent.basedir@` 替换为工程根绝对路径 → 任意工作目录启动，日志统一落工程根，不散落模块目录 |
| test | `${LOG_PATH:./logs}` | 部署系统环境变量注入日志盘 |
| prod | `${LOG_PATH}`（必填） | 缺环境变量启动失败（fail-fast），日志归基础设施托管盘 |

**落点版本**：随 Spring Boot BOM（logback 1.5.34）。

### 3.8 校验与切面：JSR-380 校验 + Spring AOP

**校验**：契约层（`opshub-api`）只引 `jakarta.validation-api` 注解（零实现依赖，独立发版不受污染，编码规范 §2.7.2），实现侧（hibernate-validator）由启动装配层 starter 装配——**注解在契约、实现在装配**，是分层规范的标准落法。高危运维操作（如 `DROP`/`TRUNCATE` 类命令的工单申请）请求参数全部走注解前置校验，实现"外部输入在系统边界即校验"（安全红线第一条）。

**切面**：Spring AOP（`spring-boot-starter-aop`，AspectJ 注解风格）支持编码规范 §2.7.1 的**双监控切面**：

- 业务监控切面：拦截对外操作接口，出口按方法返回类型反射分派"异常转结果"，实现实现层零 catch、调用方永不感知实现异常；
- 数据访问监控切面：对 DAO 做自动埋点，统一记录入参/耗时/异常——配合日志分通道，SQL 行为全部落 `DAL_ACCESS` 通道，为操作审计提供机器可读证据源。

### 3.9 语言基座：JDK 21（LTS）

选型理由（非从众，两条本项目具体动因）：

1. **虚拟线程预备**：OpsHub 大量操作是"对外部实例的 IO 等待"（连目标库执行慢查询、等待 Redis INFO）——这是虚拟线程的靶心场景。Spring Boot 3.2+ 环境 JDK 21 下仅需开启 `spring.threads.virtual.enabled` 即可让 Tomcat 工作线程切换为虚拟线程，平台在线巡检"数十实例并发采样"的线程占用问题有确定性口子（**演进原则**：现在不开，参数级开关随时可开）；
2. **ZGC**：管理面 JVM 与被管实例同宿主机部署时，GC 长尾不能干扰平台自身监控采集；
3. 配合编码规范语言规约（`record`/文本块/模式匹配）降低样板代码量。

> Spring Boot 3.5 基线要求 JDK 17+，JDK 21 是其支持矩阵内的最新 LTS——JDK 25（下一个 LTS）进入 Spring Boot 认证矩阵后一次性上收，基座变更策略保守。

### 3.11 依赖最小引用落点（能力唯一归属矩阵）

**"最小模块引用规则"的答卷**——每个依赖只允许出现在其能力唯一归属模块里，其余模块经内部依赖传递获取，禁止私引：

| 依赖 | 唯一归属模块 | 落点理由（编码规范 §2.4 矩阵 / §2.5 机制 3） |
| --- | --- | --- |
| **Spring Boot BOM** | 根 POM `dependencyManagement` | 版本唯一天字第一号登记地，子模块一律不带版本号 |
| `jakarta.validation-api` | **opshub-api**（契约层） | Request/DTO 的 JSR-303 注解载体；契约实现零依赖 |
| `slf4j-api` / `fastjson2` / `commons-lang3` | **opshub-common**（公共层） | 统一日志门面、JSON 与通用工具的收敛地；业务模块禁止直连三方件 |
| `spring-boot-starter-data-redis` | **opshub-infra-integration**（集成层） | 外部系统客户端的唯一出口——Redis 对平台是外部系统 |
| `mybatis-flex-spring-boot3-starter` + `mysql-connector-j`（runtime） + `spring-boot-starter-jdbc` | **opshub-infra-dal**（数据访问层） | DAO/DO/事务封装/数据访问组件唯一归属；驱动 runtime 作用域（编译期不可见 JDBC 细节） |
| `mapstruct` | **opshub-infra-dal** + **opshub-biz-shared** | DO↔Model（仓储体内）与 Request↔Model（模板转换器体内）两类转换器各管各的边界 |
| `spring-web` + `spring-context`（注解级） | **opshub-biz-impl**（接口实现层） | Controller/Facade 编译注解可见；**不带 Tomcat**（运行时装配留给 bootstrap） |
| `spring-boot-starter-web/aop/validation` + `fastjson2-extension-spring6` | **opshub-bootstrap**（启动装配层） | 运行时组件装配唯一出口 + 打包出口；web starter 已 exclusion Jackson 保 JSON 唯一实现 |
| `lombok`（provided） | 全部业务模块 | 编译期组件，provided 不传递、零运行时足迹 |
| `testng`（test） | opshub-test | 测试域 test 作用域 |
| **编译期处理器三件套**（lombok→mapstruct-processor→binding） | 根 POM `maven-compiler-plugin` 注解处理器路径 | 处理器顺序有讲究：先 lombok 生成访问器，mapstruct 后感知 |

**这份矩阵在工程上的验收方式**：`mvn dependency:tree` 干净、`dependencyConvergence` 全绿、重启后 Enforcer 阻断违规——具体 POM 数据已在工程主结构中落实（见仓库 `pom.xml` 及各模块注释）。

## 四、量化验证口径（四步表达法收口）

选型是不是选对了，需要事前定下游进检验的尺子（对应《架构篇》四步表达法第 ④ 步）：

| 指标 | 目标值 | 现状基线（阶段①实测） |
| --- | --- | --- |
| 应用启动耗时 | < 3s（管理面无秒级弹性诉求） | ✅ 实测 1.25s（macOS 本地，JDK 21） |
| 常规接口 RT（P99） | < 500ms（含网络与目标实例查询往返，参考《架构篇》同机房 RTT 0.1~0.5ms + 查询执行时间） | 待阶段②联调后压测 |
| 日志打印 RT 贡献 | < 接口 RT 的 1%；异步队列丢弃计数常态为 0（日志是可观测性成本，不允许成为业务面延迟的一部分，《日志通道设计说明》§9） | 管道端已达标（四通道异步 + neverBlock + pattern 无调用位置），业务代码守卫纪律阶段②随开发落地 |
| 平台自身 SLA | 99.9%（3 个 9）：管理面停机≠业务资损（业务面与管理面隔离成为可用性的**结构性缓解**，无需堆冗余到四个 9） | 结构性保障 + 实例不会因平台故障而异常 |
| 操作审计完整性 | 100%（高危操作一次不漏，靠日志通道 + DB 审计表双保险，不依赖人工调阅） | 通道已建（错误/数据访问通道） |
| 依赖安全性 | Enforcer 全绿 + 零 adminatively disabled 漏洞告警 | ✅ 阶段①全部通过 |

**失败兜底**：

- 平台不可用时，各 MySQL/Redis 实例照常运行（运维平台不在线上数据路径上）——这是本系统可用性的**结构性免死金牌**；
- 阶段②若发现多实例并发连接吞吐瓶颈（信号：巡检样本积压 > 5s），一次性开关启用虚拟线程（§3.9）验证提升；仍不足则数据巡检通道独立为作业域（按量级演进，而非容量堆砌）。
